# Unit Testing komcards-api

Repo ini punya dokumen `skills.md` di root khusus testing. Reference ini merangkumnya + konvensi nyata di test yang ada (`internal/app/card/service_test.go`, `monit/service_test.go`, `user/service_test.go`).

Stack: `testing` stdlib + `stretchr/testify` (`assert`, `mock`) + `mockery` untuk generate mock. Test HTTP memakai `net/http/httptest`.

## Aturan penting sebelum menulis test

1. **Cek dulu mock-nya ada.** Mock berada di `internal/repository/mocks/` dan `internal/client/mocks/`.
   - Jika mock untuk interface/dependency yang dibutuhkan **belum ada**, **infokan ke user** dan sebutkan perintah mockery yang perlu dijalankan — jangan generate tanpa persetujuan.
2. **Jelaskan rencana perubahan** (file test, mock yang dipakai) di implementation plan sebelum generate/menulis.
3. Test boleh ditulis dalam Bahasa Indonesia untuk nama case (`name: "1. PIN salah"`); ini konvensi yang sudah ada di repo.
4. Untuk perubahan yang menyentuh saldo/PIN/auth, test regresi sangat dianjurkan.

## Generate mock (mockery)

Format perintah dari README:
```shell
~/go/bin/mockery --dir=internal/repository --name=CardTransactionRepositoryInterface --filename=card_transaction.go --output=internal/repository/mocks
```
Beberapa interface juga mencantumkan perintahnya sebagai komentar di atas interface, mis. `internal/repository/cache.go`:
```go
// ~/go/bin/mockery --name=CacheInterface --dir=internal/repository --output=internal/repository/mocks
type CacheInterface interface { ... }
```
Versi mockery yang dipakai: `v2.53.6` (header file mock: `// Code generated by mockery v2.53.6. DO NOT EDIT.`). Jangan edit file mock manual.

- Gunakan `zap.NewNop()` untuk logger di test.
- `context.Background()` boleh di test (berbeda dengan kode produksi).
- `envVars` dipakai beberapa test untuk men-set `config.Env` sebelum memanggil service (via `envconfig`/`os.Setenv`); ikuti pola test yang ada.
- `.Once()` memastikan mock dipanggil tepat sekali; `.Maybe()` bila pemanggilan tidak pasti (mis. alur error berhenti di awal atau goroutine latar).
- Cocokkan dengan `assert.Equal(t, tt.expectedErr, err)` untuk sentinel error.

## Mocking background task (goroutine)

Menguji fungsi yang menjalankan `go s.BackgroundMethod(...)`:
1. Mock semua dependency yang dipanggil di dalam goroutine (kalau `nil` → panic nil pointer).
2. Definisikan ekspektasi `.Maybe()` agar tidak gagal saat thread latar berjalan konkuren.
3. Tambahkan `time.Sleep(10 * time.Millisecond)` di akhir `t.Run` agar goroutine sempat berjalan sebelum test ditutup.

## Interface dengan return type konkret — `repository.DummyQueue`

Beberapa method mengembalikan struct konkret (mis. `QueueInterface.WithExchange` → `*repository.Queue`), sehingga panggilan lanjutan (`.Publish`) mengeksekusi kode asli dan panic tanpa koneksi RabbitMQ.

Solusi bersama: gunakan helper global `repository.DummyQueue` (di `internal/repository/dummy_queue.go`):
```go
package repository

type DummyQueue struct {
    QueueInterface
}

func (d DummyQueue) WithExchange(exchange string) *Queue {
    select {} // block background goroutine forever, avoid real .Publish() panic
}
```
Di unit test: gunakan `repository.DummyQueue{}` sebagai `Queue`. Karena dipusatkan di package `repository`, helper ini bisa diimport dari test package mana pun tanpa circular dependency. Jangan menyalin definisinya ke tiap test.

## Test HTTP handler

```go
func TestGetUserHandler(t *testing.T) {
    h := NewHandler(f) // atau handler dengan mock service

    req := httptest.NewRequest(http.MethodGet, "/users/1", nil)
    rec := httptest.NewRecorder()

    // panggil gin handler
    c, _ := gin.CreateTestContext(rec)
    c.Request = req
    h.GetUser(c)

    assert.Equal(t, http.StatusOK, rec.Code)
}
```

## Menjalankan

- Semua test: `go test ./...` (atau `make test`).
- Coverage: `make test-coverage` / `make test-coverage-detail` (`go test -coverprofile=coverage.out ./...`, `go tool cover`).
- Race detector: `go test -race ./...`.
- Fokus package: `go test ./internal/app/card/...`.
